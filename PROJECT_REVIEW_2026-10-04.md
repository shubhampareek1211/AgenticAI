# Project review — 2026-10-04

We have a working local cricket assistant with voice input and spoken answers,
plus separately deployed private speech APIs. We have not yet delivered the
complete cloud application that any verified Columbia mailbox holder can use.
The main remaining work is speech acceptance, cloud application integration,
real authentication/database deployment, and release validation.

This review inspected the source, original build/voice plans, saved benchmark
evidence, live Cloud Run inventory/configuration, enabled project APIs, and
port 8001's public configuration endpoints. It did not rerun full regression
tests, change cloud services, provision infrastructure, or benchmark inference.
User-reported curl timings are identified separately below.

**What we intended**

The original product is a deployed Gemini cricket analyst for men's ODI/T20I:
persistent conversations, external cricket data, deterministic statistical
tools, visible tool results, charts, and the original teammate-dismissal
analysis. Voice expanded this to record → transcribe → review/edit → Send →
answer → optional spoken playback. The selected cloud audience is any verified
`@columbia.edu` mailbox, using email links rather than a Google-account/domain
membership requirement. The pilot should be low-cost, accept downtime, keep
workers private, and preserve the existing IAP-protected service.

The working design uses three distinct responsibilities:

`recording → Whisper → editable text → Gemini/tools → saved answer → Kokoro → audio`

It is turn-based. The app generates Kokoro audio from a completed saved answer;
it does not yet speak while Gemini is still reasoning/generating. Streaming
short synthesized WAV segments is implemented, but live partial transcription,
continuous conversation and interruption of an in-progress voice agent are not.
A single unified speech/reasoning model was discussed, not implemented.
The code's reasoning default is `vertex_ai/gemini-3.5-flash-lite`; runtime
environment overrides remain possible. This review does not certify a new
model selection or infer the old cloud app's model from that default.

**Performance: what the numbers establish**

| Observation | Interpretation |
| --- | --- |
| User's first curl took about 55 seconds; immediate repeat took 2.88 seconds | A warm short-answer API call is useful. The difference suggests startup contributed substantially, but that first request was not traced, so its delay cannot be attributed entirely to a cold start. |
| Recorded warm Kokoro short phrase: 1.99–2.27 s; longer phrase: 6.13–6.73 s | Small synthetic measurements; insufficient for a production p95. Short phrase generated 3.9 s audio; longer phrase generated 10.85 s. |
| Kokoro deployment startup to probe readiness: 30.1 s | Startup itself exceeds the provisional 20-second cold target in this observation. This is separate from the user's 55-second request. |
| Two concurrent longer Kokoro calls: 6.43 and 13.42 s | Both succeeded, but one experienced waiting. This does not demonstrate low-latency simultaneous capacity. |
| App TTS client: first WAV at 7.68 s, second at 15.88 s | Confirms real application-client integration through the authenticated proxy. It excludes the earlier transcription, Gemini answer, and browser playback stages. |
| Whisper 2-CPU/four-thread synthetic sample p95: 9.67 s; 8-CPU/eight-thread: 4.22 s | Earlier small comparison, not the current two-thread baseline's p95. Names were misrecognized. Eight CPUs were not adopted; deployed baseline remains two CPUs. |

The full user wait contains audio upload/normalization, transcription, Gemini
and tool work, speech generation, transfer, and browser playback startup.
The editable transcript and Send step also introduce intentional user interaction.
No complete end-to-end latency distribution has been measured. A 2.88-second
TTS request therefore does not imply a 2.88-second voice conversation.

**Remaining work in dependency order**

1. **Establish the final speech configuration with measured evidence.** Use the
   local app against the cloud workers for a controlled evaluation, retaining
   rollback to local workers. Measure Stop-to-edit, chat/tool time, and
   first-audible-answer separately, both warm and cold. Prioritize Whisper
   accuracy and latency; another TTS short-sentence curl is not the main missing
   proof. Validate the planned English/Hindi/mixed corpus: 20 short questions,
   five long clips, and five silence/noise controls per group. Preserve
   ≥18/20 essential-meaning retention per group, no transcripts for controls,
   warm short-clip p95 ≤5 s and cold short-clip ≤20 s. Test Kokoro names,
   numbers, longer answers, and its separate warm/cold targets. If a gate
   fails, benchmark a documented runtime/model/provider revision within the
   cost constraint. Your approval of the 2.88-second example does not by itself
   waive the long-answer, cold-start, or multilingual gates.
2. **Complete the deployable application prerequisites.** Configure Firebase
   email links and test a real Columbia mailbox, expired/reused links,
   non-Columbia rejection and token lifecycle. Price the exact zonal Cloud SQL
   pilot configuration before provisioning; apply migrations through
   `0004_voice_daily_usage`, load the intended data, and validate persistence.
   Record total app, Gemini, speech, database, auth, storage/build/log costs.
3. **Deploy a separate pilot app and wire the private APIs.** Use its own
   service identity with scoped worker Invoker, database and secret access;
   enforce `APP_ENV=pilot`. Verify real backend-to-worker ID tokens and audience
   settings for both APIs. Test sign-in → record → edit → chat/chart → playback
   from the deployed browser, and persistence after restart. Keep existing IAP
   traffic unchanged. Speech settings should enforce private HTTPS/IAM in pilot
   mode just as TTS settings do; today STT configuration validates the selected
   auth mode but does not require IAM/HTTPS solely because it is a pilot.
4. **Finish release testing and operational controls.** Test cross-user and
   legacy session denial, mobile microphone/autoplay behavior, long answers,
   worker failure, two users and overload, memory under uploads, text-chat
   responsiveness, disconnect behavior, backups/restore and rollback. A
   playback Stop or Cloud Run timeout does not guarantee worker inference stops.
   Confirm usage limits suit the pilot: defaults are 10 combined voice attempts
   per user/day and 100 globally; transcription plus generated playback can
   consume two attempts for one exchange, so ten is not ten full voice turns.
5. **Produce and release a reviewable snapshot.** Consolidate stale planning
   statements, run required tests/builds for the exact candidate, record image
   digests and data version, and commit the intended source. Do not push to the
   legacy auto-deploy branch casually. Start with a small Columbia pilot cohort
   and monitor error rates, stage latency, usage and cost before expanding.

Prior verification records show 228 backend tests passing with one worker-
dependency skip and 39 frontend tests passing. The later image test exercised
the real Kokoro worker. These are preserved historical results, not new test
runs in this review; none replaces the live cloud acceptance gates above.

**Assessment**

The local prototype and private cloud APIs are achieved. Secure public-pilot
integration and predictable speech performance remain. The next useful
milestone is one measured, authenticated, persistent browser workflow using
the selected cloud services—not simply another model endpoint. Do the speech
validation before committing to database spend and the full release.
